# Kindling run data — schema v1

Structured outputs of a headless run, for tools and later for the live stream / replay.
The version is `civ_core::data::DATA_SCHEMA` (currently **1**), written as `schema` in
`manifest.json` and `summary.json`. The text report on stdout is unchanged and still supported
by the tools.

```
kindling --headless --seeds 1..10 --years 500 --out out/data [--out-genealogy] [--save 'out/s{seed}.civsave']
```

writes, per seed, `out/data/seed-S/`:

| file | what | size (256×160, 500 y) |
|---|---|---|
| `manifest.json` | how the run was made | ~2 KB |
| `metrics.csv` | one row per year played in this run | ~150 KB |
| `summary.json` | end-of-run summary (everything in the text report, as data) | ~20–40 KB |
| `chronicle.ndjson` | the chronicle (major events), one JSON object per line | ~10–100 KB |
| `frames.ndjson` | the history store's frames (see below), one per line | ~0.2–0.5 MB |
| `genealogy.csv` | only with `--out-genealogy`: every founding, split, merge, death, drift landing, absorption | 1–5 MB; tens of MB on 800×800 |

`--save` accepts `{seed}` in the file name (one save per seed in a multi-seed run).
Writing outputs never changes the run: the report and the save are byte-identical with and
without `--out`.

## manifest.json

| key | meaning |
|---|---|
| `schema` | data schema version (1) |
| `kind` | `"kindling-headless-run"` |
| `program`, `version` | `kindling`, crate version |
| `git_sha` | commit the binary was built from (`+dirty` if the tree had changes; `unknown` without git) |
| `seed`, `map_w`, `map_h` | world |
| `loaded_from` | save the run continued from, or null |
| `start_year`, `end_year`, `years_requested` | years covered by this run |
| `threads` | rayon worker threads |
| `save_format`, `saved_to`, `save_bytes` | save format version; the save written, if any |
| `t_gen`, `t_run`, `t_save` | seconds: world generation (or load), simulation, saving |
| `started_unix`, `command` | when and how it was started |
| `params`, `config` | the full `Params` and `Config` used |

## metrics.csv

One row per year closed during this run (a continued run starts after the loaded save's last
year). Columns, in order:

1. every `YearStats` field in declaration order (`year, pop, bands, items_world, ...`; the
   names are the `civ_core::world::YearStats` field names; a missing value is an empty field);
2. `c_<counter>` for every `Counters` field (`civ_core::world::Counters::NAMES`, generated by
   the `counters!` registry, so a new counter appears automatically): how much the counter
   rose during that year. `max` counters (`c_max_fight_deaths`) carry the value at the year end.

Adding columns is not a schema change; tools must select columns by name. Renaming or
removing one is (bump `DATA_SCHEMA`).

## summary.json

`{schema, seed, summary, conflict, counters, event_rings, archive}`:
`summary` is `civ_core::analysis::Summary` (the text report's data), `conflict` the conflict
block of the text report, `counters` the run totals by name, `event_rings` how far back each
event ring reaches (`{lore|conflict|life: {len, from_year}}`), `archive` the history store's
extent (`frames`, `decadal`, `genealogy`, `weddings_kept`, `begun_year`).

### Crossing ledger (inventions step 0)

Additive fields, no schema change:
- `metrics.csv` / `YearStats`: `boat_bands`, `sail_bands` (boats and the seacraft to use a sail),
  `seacraft_mean`, `seacraft_p90` (over bands with boats), `rumour_share` (bands holding word of
  a far shore), `leg_record` (longest crossing to another landmass so far, open-water cells).
- counters: `crossing_cells` (open-water cells of all crossings; mean leg = `crossing_cells /
  crossings`), `voyages_provisioned` (planned voyages with food put by), `longest_leg` (a `max`
  counter, cells, rounded).
- `summary.sea`: `longest_leg`, `mean_leg`, `voyages_provisioned`.
- `summary.continents[]`: `leg` and `tech` of the first arrivals.
- `summary.crossings[]`: every landmass first reached over open water, in order:
  `{year, landmass, continent, from, leg, gap, tech}`. `tech` lists names from
  `civ_core::world::TECH_NAMES`: `outrigger`, `sail`, `plank`, `provisioned`, `ship`, `jar`,
  `pilot`, `sky`, `route`, `expedition` (step 5b), `adrift` (bits reserved for later steps stay unset until then).
- `world.landfalls[]` in saves: `leg`, `tech` (bitmask), default 0.
- event kind `LongestCrossing` (id 35, major): a crossing to another landmass over more open
  water than any before it (at least 3 cells). `band` came ashore at `x, y` on landmass
  `other` after `recipe` cells; `item` is the boat (unset when adrift).

## Event records (chronicle.ndjson; the event feed)

`civ_core::data::event_record`:
`{"t": tick, "year": t/4, "kind": "Split", "band": id, "other": id, "x": .., "y": .., "item": id, "recipe": i, "text": "..."}`.
`x, y` are the cell; `item` / `recipe` / `other` are left out when unset (u32/u16 "none").
`kind` is the `EventKind` name. For genealogy kinds: Split (band = parent, other = daughter),
Merged (band joined other), Drifted (band = home band, other = new band), Absorbed (other took in
band's last people; recipe = how many).

## frames.ndjson (the history store)

One `civ_core::archive::Frame` per line, oldest first:
`{year, span, counters, kinds, lineages, regions, grid, lore, weddings}` —
`year` is the last year covered, `span` the years covered (1, or 10 for folded decades);
`counters` counter increases over the span; `kinds` events per `EventKind` (index = kind id);
`lineages` rows `[lineage, bands, people, cells, mean recipes]`; `regions` rows
`[landmass, bands, people, farming bands, mean recipes]`; `grid` people per block of an 8×8 grid
over the map (row-major); `lore` rows `[item, bands able to make it, times learned, times
forgotten]`; `weddings` rows `[lineage a, lineage b, count]`. Snapshots are at the end of the
span, tallies are summed over it.

### Pitch and sealed jars (inventions step 1)

- New material `pitch` (25) and form `Jar` (25; "sealed jar"), item ids `25` (raw pitch) and
  `25*32+mat` (jar). They appear in `discovery order`, chronicle `FirstInvention`, item counts
  and the lore events like any other item; no new event kind.
- `metrics.csv` / `YearStats`: `pitch_bands` (bands that can make pitch), `jar_bands` (bands
  with sealed jars).
- Crossing ledger: the `jar` bit of `tech` is set when the crossing band had jars.
- Save format v11 (see `SAVE_FORMAT.md`): per-material band vectors are 26 long.

### Provisions and endurance (inventions step 2)

- No new item, event kind or save field: drying racks and cold cellars are practices read off a
  band's kit and its cell's climate; endurance is worked out when a band puts to sea.
- `metrics.csv` / `YearStats`: `dried_bands` (bands drying meat and fish on racks),
  `cellar_bands` (bands with cold cellars), `endurance_p50` / `endurance_p90` (endurance in
  open-water cells of bands with boats, as if they sailed from where they are).
- Counter `past_endurance`: planned voyages longer than the crew's endurance (in
  `counters`, `summary.json` `sea.past_endurance`, and the text report's crossing-ledger line
  as a share of voyages). `summary.json` `sea.endurance_p90` is the last year's value.
- `voyages_provisioned` and the ledger's `provisioned` bit keep their meaning: food put by in
  full (store >= half a season's food per person, or a plank boat).

### Pilotage and remembered routes (inventions step 3)

- Band field `pilot` (0..1, additive: saved after `carry`, older rows load as 0): reading
  signs of land out of sight of it. On the water a band steers toward land on another landmass
  once it is within 10 x `pilot` cells (the `World::sea_signs` field: per sea cell, steps to and
  cell of the nearest land, derived from the map, not saved). Signs never add range.
- `metrics.csv` / `YearStats`: `pilot_bands` (bands with pilot > 0.1), `pilot_mean` /
  `pilot_p90` (over bands with boats).
- Counters: `aimed_voyages` (planned voyages steered for a far shore the band had word of) and
  `sign_voyages` (planned voyages that turned toward signs of land on the way). In `counters`,
  `summary.json` `sea.aimed_voyages` / `sea.sign_voyages` / `sea.pilot_bands` / `sea.pilot_mean` /
  `sea.pilot_p90`, and a "pilotage" line (shares of voyages, per-seed pilot mean/p90) in the
  multi-seed text report.
- Crossing ledger: the `pilot` bit is set when the crossing crew turned toward signs; `route`
  when the band held word of the far shore longer than an ordinary rumour lasts (50 years) -
  pilots keep it up to 3x as long.

### Sky lore (inventions step 4)

- Band field `sky` (0..1, additive: saved after `pilot`, older rows load as 0): a calendar and
  star paths. Settled farmers learn it (0.003 x sow x settled per season, when both are above
  0.3), and so do crews out of sight of land on a leg survived (0.003 per open-water cell up to
  25, times pilot / 0.3 up to 1). It fades 0.998 per season, passes to daughters and drift
  parties, and is taught (like pilotage) to neighbours who farm or have a little pilotage.
- Effects: sowing effort (the plough factor) x (1 + 0.05 x sky); at sea it counts only as far
  as the crew has pilotage, `sky_at_sea` = sky x min(pilot / 0.3, 1), and an aimed heading's
  error shrinks by 0.6 x `sky_at_sea` (0.15 -> 0.06 for a seasoned crew). Sky lore adds no range.
- `metrics.csv` / `YearStats`: `sky_bands` (bands with sky > 0.1), `sky_farm_mean` (over bands
  that sow), `sky_sea_mean` and `sky_at_sea_mean` (over bands with boats).
- Counter `sky_voyages` (voyages whose crew had `sky_at_sea` >= 0.2). In `counters`,
  `summary.json` `sea.sky_voyages` / `sea.sky_bands` / `sea.sky_farm_mean` / `sea.sky_sea_mean` /
  `sea.sky_at_sea_mean`, and a "sky lore" line in the multi-seed text report.
- Crossing ledger: the `sky` bit is set when the crossing crew had `sky_at_sea` >= 0.2.

### Ships (inventions step 5)

- Form `Ship` (form id 26, appended after `Jar`; item id `26*32+mat`, e.g. 832 "nailed plank
  ship" for wood). Recipe (combine, by the water only): a plank boat + raw pitch + a metal point
  (any malleable metal: copper, bronze, iron) makes a ship of the plank's material, success
  0.2. It sits in a new kit slot `ship` (scored by the boat quality of its material); `Kit`
  is derived each season, so it is not saved.
- Tinkering: a band that already has a plank hull and lives by the water weighs planks, pitch
  and metal points by an extra `3 x seacraft` when it picks things to try together (the same
  need-weighting as the other forms), so seafaring shipwrights try the combination far more
  often than inland bands.
- Effects: endurance (provisions) x 1.4 x (1 + 0.2 x ship quality); boat range x 1.25 but
  only with a usable sail (sail in kit and sailing experience > 0.4). No extra seaworthiness:
  a ship hull counts for `boat_q` exactly like a plank hull. Ships need pitch caulking upkeep
  like other craft.
- `metrics.csv` / `YearStats`: `ship_bands` (bands with a ship), `ship_q_mean` (mean ship
  quality over them).
- Counter `ship_voyages` (voyages made in a ship). `summary.json` `sea.ship_voyages`,
  `sea.ship_bands`, `sea.ship_q_mean`, `sea.first_ship_year` (from the `FirstShip` event, null
  if none); a "ships" line in the multi-seed text report.
- Event kind `FirstShip` (id 36, major): the first time a band in a ship (not adrift) comes
  ashore on another landmass; `other` = landmass, `item` = the ship, `recipe` = leg in cells.
- Crossing ledger: the `ship` bit (`TECH_SHIP`, 1<<4) is set when the crossing crew had a ship.

### Expeditions, mat sails and deep-water seamanship (inventions step 5b)

- Planned expeditions: on a planned voyage (a band moving, or a daughter band setting out; not
  scouting, flight or drift) a crew with a ship, stores for everyone (store >= half the people)
  and food that keeps (`preserved` >= 0.8: salt, dried, grain, jars or cheese) sails as far as
  its endurance, if that is more than its usual reach (boat range x e^(0.25 ambition)). Boats
  without a ship are unchanged.
- Mat sails: recipe (combine, by the water only) a plank boat or ship + a shaft + a woven
  basket (plant-fibre matting) makes a "woven mat sail" (`Sail` of `Fibre`, item 21*32+Fibre),
  success 0.05. A sail is usable only with seacraft > 0.4 and, for a mat sail, only with a
  plank hull or ship in the kit (`World::sail_usable`); on a dugout or canoe it does nothing.
  The kit keeps a cloth sail before a mat one.
- Deep-water seamanship: a ship crew that comes through a leg of `sea` >= 6 cells (out of
  sight of land) gains seacraft `0.004 x (sea - 6)` of the way to 1 on top of the usual lesson,
  and pilotage `2 x 0.003 x sea` (the whole leg, instead of 0.003 per cell up to 25 cells).
  Sky lore is learnt as before (it still needs pilotage to read).
- Counters `expeditions` (planned voyages past the usual reach on expedition stores),
  `deep_water_legs` (ship legs >= 6 cells survived). `metrics.csv` / `YearStats`:
  `mat_sail_bands`. `summary.json`: `sea.expeditions`, `sea.deep_water_legs`,
  `sea.mat_sail_bands`, `sea.first_mat_sail_year` (null if never); an "expeditions" line in the
  multi-seed text report.
- Crossing ledger: the `expedition` bit (`TECH_EXPEDITION`, 1<<9) is set on crossings made on
  expedition range. `tech` names now include `expedition`.
- No save format change: no new saved band fields; counters and year stats default to 0 in
  older saves.

### Iron in the fields (inventions step 6)

- New saved per-cell layer `World::opened` (0..1, serde default empty, so older saves load and
  the layer is sized on first use): how far a cell's forest or heavy ground has been opened for
  fields. Derived (not saved) `open_pot`: the crop potential the cell would have once fully
  opened (crop potential with the forest penalty mostly lifted - TempForest 0.9, TropForest 0.55,
  Taiga 0.3 of the way up - and up to x1.25 on heavy wet ground, rain 0.6-0.9).
- A band whose toolkit can make an iron axe or edge (`iron_tools`) farms against the opened
  potential; others farm against `crop_pot + opened x (open_pot - crop_pot)`, so ground opened
  by iron users stays better for all. Iron-using farmers open 0.06 x sow x weather of the gap per
  season and plough 1.15x as well. Opened ground fades (x0.995 a year) where fields are no
  longer tended (tend < 0.4).
- `metrics.csv` / `YearStats`: `iron_farm_bands` (farming bands with iron tools),
  `opened_fields` (field cells with opened > 0.1), `forest_fields` (field cells in forest
  biomes), `wet_fields` (field cells with rain >= 0.75).
- Counter `iron_clearing` (band-seasons that opened ground). `summary.json` `farming.first_iron_farm_year`
  (first year with an iron-farming band, null if never), `farming.iron_farm_bands`,
  `farming.opened_fields`, `farming.forest_fields`, `farming.wet_fields`, `farming.iron_clearing`; an
  "iron in the fields" line in the multi-seed text report.
- No save format change (the new layer defaults to empty).

### Steel (inventions step 7)

- New material `Steel` (26; save format v12). Recipe: Heat of wrought iron with bellows in a
  closed charcoal kiln, by water (the quench), chance `STEEL_P` = 0.03 per try. Shaped like
  iron (a hammerstone works it hot) into knives, points, spears and axes; traded like iron.
  Props: hard 6, tough 9, sharp 9, malleable 5.5 (cut 0.78 against iron 0.64 and bronze 0.65).
- Fights get deadlier only through the edge: casualties already scale with
  `0.6 + weapon_q`, and a steel spear and axe raise `weapon_q` by about 0.07 over iron.
  Armour (shields, bows: `loss_guard`) is unchanged. Steel tools count as iron in the fields.
- New stage `steel` (above `iron`) in `stage_now` / `stage_ever` and the stage table.
- `metrics.csv` / `YearStats`: `steel_bands` (bands with a steel knife, point, spear or axe in
  their kit), `weapon_q_mean` (people-weighted mean `weapon_q`).
- Counter `steel_made` (band-seasons a band forged fresh steel). The world first of the steel
  bar is a `FirstInvention` event (no separate event kind).
- `summary.json` `metal.`: `first_steel_year` (null if never), `steel_bands`,
  `steel_bands_peak`, `steel_made`, `weapon_q_mean`, `weapon_q_peak`, `fights`,
  `deaths_per_fight`; a "steel" line in the multi-seed text report.

### Tallies, tokens and records (inventions step 8)

- New form `Mark` (id 27; no format bump: appended, so older item ids are unchanged). Recipes:
  Combine a good edge (cut > 0.3) with a wooden stick or a raw bone: a tally (p 0.3); Shape soft
  clay with a point: a clay token (p 0.3); Heat a clay token like a pot: a fired clay token.
  Names "tally stick", "notched bone tally", "clay token", "fired clay token". The kit keeps
  the best in `Kit::mark` (a fired token first).
- Band fields (saved, appended after `sky`; older saves load them as 0):
  - `records` (0..1): grows by `RECORDS_GAIN` (0.04) of the way to 1 each season a band with a
    mark has something to count (`World::keeps_count`: a store of `RECORDS_STORE` = 2 seasons'
    need, `RECORDS_PARTNERS` = 4 ties of 0.5 or more, a herd, or tribute owed); fades by
    `RECORDS_FADE` (0.97) a season. Full records: stored food spoils 5% less, unused recipes are
    forgotten 25% more slowly, trade ties fade 0.9 a year instead of 0.8 and the band keeps
    up 1.5x as many. Records spread by teaching to bands that have something to count.
  - `owed` (0..1): tribute paid or taken sets it to 1 on both sides; fades 0.95 a season.
- The 8-partner cap is gone. (Step 8 faded every tie by `keep^(spread^2)`; replaced in step 8b,
  below.)
- An unused mark (nothing to count) is not practised, so it can be forgotten like any idle item.
- Event `FirstRecords` (kind 37, major): the first band with records >= 0.3 (item = its mark).
- Counter `marks_used` (band-seasons a band kept count with its mark).
- `metrics.csv` / `YearStats`: `mark_bands`, `records_bands` (records > 0.1), `records_mean`,
  `partners_mean`, `partners_max`.
- `summary.json` `records.`: `first_records_year`, `first_mark_year`, `mark_bands`,
  `records_bands`, `records_bands_peak`, `records_mean`, `marks_used`, `counting_bands`,
  `records_where_counting`, `partners_mean`, `partners_max`, `partners_mean_peak`; a "records"
  line in the multi-seed text report.

## Inventions step 8b: close ties (no format bump)

- Tie upkeep (`Band::fade_ties`, yearly): a band's care budget is `TIE_CARE` = 4 x (1 +
  `RECORDS_SPAN` 0.5 x records). Each tie's weight is `w` = trade strength + marriage tie +
  kinship with that partner; it gets `TIE_CARE x w / sum(w^2)` of full upkeep (at most 1).
  Strength is multiplied by `LOOSE_KEEP` (0.3) + (`full` - 0.3) x that share, `full` = 0.8 +
  0.1 x records. So a band with few ties keeps them all up (x0.8), and one with many keeps up
  its strongest and lets loose ones fade towards x0.3 a year. Ties under 0.05 (and not married)
  are dropped. No cap and no set number of close ties.
- `CLOSE_TIE` = 0.3: a trade tie this strong counts as close (food for the hungry and gifts
  pass along it, as between kin of 0.2+), unchanged in value.
- `metrics.csv` / `YearStats`: `close_ties_mean`, `close_ties_max` (ties of `CLOSE_TIE` or more
  per band after the yearly fade).
- `summary.json` `records.`: `close_ties_mean`, `close_ties_max`; the headless "records" line
  adds `k<mean>/<max>`.

## Inventions step 9: charts (no format bump)

- A band **keeps charts** (`World::charts`) when records >= `CHART_MIN` (0.4), pilotage >=
  0.4 and it has a boat (the chart is kept while it is used). No new item.
- A charted band's far-shore route does not fade: each sea season it is renewed
  (`far_shore_year` = this year) instead of being forgotten after `rumour_keep` years.
- Teaching: when a charted band passes word of its far shore in `exchange`, the reach is x
  `CHART_TELL` (1.5) and the chance is `CHART_TEACH_P` (0.6, plain word 0.3); a taught route
  arrives as fresh (year = now).
- Event `FirstChart` (kind 38, major): the first band keeping charts (`other` = landmass of
  its far shore, or none). No minor events for kept/faded routes (counters only, to keep the
  chronicle quiet).
- Counters `routes_kept` (far-shore routes renewed by a chart), `routes_faded` (routes
  forgotten), `routes_taught` (routes passed on by a charted band).
- `metrics.csv` / `YearStats`: `chart_bands`, `charted_routes` (charted bands that hold a
  far-shore route).
- `summary.json` `charts.`: `first_chart_year`, `chart_bands`, `chart_bands_peak`,
  `charted_routes`, `routes_kept`, `routes_faded`, `routes_taught`; a "charts" line in the
  multi-seed text report.

## Inventions step 10: feasts and ale (no format bump)

- **Ale** is `item(Form::Jar, Mat::Grain)` (no new form or material): a `Combine` of raw grain
  and a sealed jar (any jar but an ale jar), only at the water's edge (`Ctx::water`), p 0.2.
  It fills the new derived `Kit::ale` slot (named "ale").
- A band **brews** (`World::brews`) when it knows ale, sows grain, has grain in stock and the
  warmest season at its cell reaches `ALE_WARM` (18 C, temp + seasonal swing). Brewing makes
  `ALE_FOOD` (5%) more food of the grain digest, and doubles (`ALE_DRAW`) a feast's draw.
- **Feasts** (`World::feast`, in a peaceful full meeting after marriage): the band with the
  larger surplus (store beyond `FEAST_KEEP` = half a season of its need, while eating fully)
  gives the other `FEAST_SHARE` (25%) of it, at most `FEAST_EAT` (1) season of the guest's
  need; no feast under `FEAST_MIN` (0.5 person-season). Host and guest bond by `FEAST_TIE`
  (0.1) x draw.
- **Prestige from giving**: the host gains `PRESTIGE_GIVE` (0.01) x food given x draw, in
  proportion to the gift; food given to the hungry in `trade` earns the same (draw 1). The old spare-labour term
  (`PRESTIGE_SURPLUS`) and flat gift (`PRESTIGE_GIFT`) are gone; fine work and voyages are
  unchanged. Nothing is capped.
- Events: `FirstFeast` (kind 39, major; band = host, other = guest, item = ale if poured,
  recipe = food given, rounded) and `Feast` (kind 40, history-store tally only, never in the
  event log). `farm_flags` bit `FLAG_FEAST` (1<<11) marks the first feast as reported.
- Counters `feasts`, `ale_feasts` (feasts with ale), `ale_brewed` (band-seasons brewing).
- `metrics.csv` / `YearStats`: `feasts`, `feast_food` (person-seasons given at feasts this
  year), `ale_bands`, `brew_bands` (year end), `prestige_size_r` (Pearson r of prestige with
  band size across bands), `prestige_top_pct` (top band's share of all prestige, %),
  `prestige_gini`. All `serde(default)`, so older saves and metrics load with zeros.
- `summary.json` `feasts.`: `first_feast_year`, `first_ale_year`, `feasts`, `ale_feasts`,
  `ale_brewed`, `feast_food`, `food_shared`, `ale_bands`, `ale_bands_peak`, `brew_bands`,
  `prestige_size_r` (end), `prestige_size_r_100` (mean, last 100 years), `prestige_top_pct`,
  `prestige_top_pct_100`, `prestige_top_pct_max` (from Y100), `prestige_gini_100`; a "feasts"
  line in the multi-seed text report.

## Inventions step 10b: feasts and ornaments scale with band size (no format bump)

- A feast gives at most `feast_cap` = `FEAST_EAT` (1) season of food for a crowd the size of
  the host or of the guest band, whichever is bigger (step 10: the guest's need only). Share,
  keep-back, minimum and prestige per unit of food are unchanged (standing stays
  proportional to the food given).
- Ornament standing a season: `ornament_prestige` = `PRESTIGE_FINE` x (0.5 + fine) x
  sqrt(pop / `ORNAMENT_SEEN`) (25); a 25-person band earns what every band earned before.
- The `Feast` tally (kind 40) is added to the history store once a year from `feasts`
  (`Archive::note_many`) instead of through an effect per feast; only the world's first feast
  still goes through the effects (for `FirstFeast`). Same tallies, cheaper.

## Inventions step 11: native gold (save format v13, map generator 5)

- **Map generator 5** adds deposit bit `D_GOLD` (128) and nothing else. Gold has its own
  random stream (`seed ^ GOLD_SALT`), so with that bit masked off a generator-5 map is byte for
  byte the generator-4 map (test `gold_leaves_every_other_map_layer_identical`, hashes recorded
  with the step 10b build). Quartz veins: max(2, land cells / 2500) veins of 1-4 cells, started
  on land at 600-3000 m, each cell kept if above 300 m. Placer gold: on river cells up to 40
  steps downstream of a vein cell (not the first step), chance 0.35 each.
- **Older maps get no gold**: `Map::upgrade_legacy` does not add it; such a map keeps
  `gen_version` 4, and binary saves of it decode against `Map::generate_layers(.., false)`
  (the generator-4 map). Only a newly generated map has gold.
- Material `Gold` (27, appended; item ids unchanged). Props hard 2.5, tough 5, sharp 1,
  malleable 10, melt 1064, new prop `prized` 1.0 (0 for every other material). Not a metal for
  tools or fields (`Mat::is_metal` false). Gathered from `D_GOLD` cells like other deposits;
  rare in the band's wants; wears as slowly as metal; strong attention (1.0) once seen.
- Recipe: `Shape` of a raw gold nugget with a hammerstone at least as hard (2.5) gives a gold
  ornament ("gold ring"), p 0.4. Nothing else: no gold tools.
- The kit wears the ornament with the highest `hard + 1 + 10 x prized`, so gold first. Ornament
  standing uses `ornament_prestige(fine + prized, pop)`: a gold ornament adds 1 to the quality
  term, i.e. 2-3x the standing of a plain ornament of the same work. Local only: gold is not in the
  trade list and standing is the wearer's own.
- `metrics.csv` / `YearStats`: `gold_bands` (bands wearing gold), `gold_held` (bands holding
  any gold), `gold_prestige_x` (mean prestige of gold wearers / mean of all bands; 0 = none).
  `serde(default)`.
- `summary.json` `gold.`: `gold_cells`, `first_gold_year`, `gold_bands`, `gold_bands_peak`,
  `gold_held`, `gold_prestige_x_100` (mean over the last 100 years with any gold wearer); a
  "gold" line in the multi-seed text report.
- Save format v13 (migration `v12_to_v13`): per-material vectors grow by one; see
  SAVE_FORMAT.md.

## What a save keeps (format v13)

| what | resolution | kept |
|---|---|---|
| `history` (`YearStats`) | yearly | whole run |
| chronicle (major events) | every event | whole run |
| archive frames | yearly | last 100 years |
| archive frames | per decade | everything older (since the store began) |
| genealogy | every event | whole run |
| single weddings | every event | last 10 years |
| event log `lore` (learned / forgot) | every event | last 20 000 (per-item tallies go to the frames) |
| event log `conflict` (fights, flights, tribute, absorption) | every event | last 40 000 |
| event log `life` (everything else) | every event | last 40 000 |

Saves from before v10 start their archive at the year they are loaded (`begun`).

## How the live stream and replay (phases 1–2) plug in

Nothing below is built yet; these are the seams left for it.

- **Metrics frame**: at each year close the world pushes a `YearStats` and closes a `Frame`
  (`World::archive_year`). A stream sends `{year_fields(yearstats), frame}` — the same data
  as one `metrics.csv` row plus one `frames.ndjson` line — so the dashboard and the files share
  one schema.
- **Event feed**: every event goes through `World::push_event` (and weddings through
  `note_wedding`), which already feeds `Archive::note`. A stream subscriber hooks there and sends
  batches as `codec::encode_events` blobs (compact, versioned `EVENTS_V`) or as
  `event_record` JSON for humans.
- **Replay**: the save's `history` + archive frames + genealogy rebuild the timeline of a run
  without re-simulating it (yearly for the last century, decadal before); exact replay of a
  stretch = load the nearest save and re-run it (runs are deterministic for a given seed and save).
- **Manifest**: the stream's hello message is the manifest.
- Versioning: the stream carries `DATA_SCHEMA` and the blob layout numbers; tools reject a
  schema they do not know (`tools/collect_runs.py`).

## Tools

- `tools/collect_runs.py DIR [OUT]` → `runs.csv` (one row per seed) and `metrics-all.csv`
  (all seeds' metrics with a `seed` column).
- `tools/agg_results.py RESULTS [BASELINE]` accepts a text report or an `--out` directory for
  either argument (same rows), so new structured runs compare against old text baselines.
- `tools/sum_results.py` (text) is unchanged.
- The `headless-sims` workflow runs with `--out out/data`, uploads it with the results and
  aggregates the structured outputs, falling back to the text report.
